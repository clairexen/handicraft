# Overview of the Architecture

## Input/Output Embedding Spaces

The learned embeddings span only half of the transformer data path width.

The input embedding space lives in the even positions of the transformer
data path and the output embedding space lives in the odd positions of the
transformer data path. (This representation is especially useful for the
"multi-cycle" thinking mode, as it makes it very easy for the model to
preserve and process relevant input token data while iteratively refining
the output token data.)

## Transformer

The transformer stack itself is a rather "classical" GTP-2 like design,
with LayerNorm's in the input paths to multi-head self-attention and MLP
building blocks, using GELU activations, and RoPE.

# Detailed Specification

This is the hand-written reference spec, the definitive source of information
about the intended design behavior, mostly directed at AI agents (= OpenAI Codex).

## GRCE and XCTX data path spec

GRCE and XCTX both sample the n_layer input vectors to the transformer blocks
in the stack at a position, mix with a recurrent GRCE or XCTX signal (G or X),
remix, and update the recurrent signal (G' and X'), and then inject the context
information into the transformer layers at later positions. Each has a
per-layer sample stage, a shared mix and remix stage, and then a per-layer
bias-injection stage in the next position. In the current implementation the
bias injection point uses

	LN(S_i + alpha .* XCTX_Bias_i) + LD(GRCE_Bias_i),

with per-feature learned gains in alpha, and where LD (Layer-Dampening) is a
LayerNorm-like operation that removes the mean and applies per-feature (and
per-layer and per-injection-point) learned gains, but replaces hard RMS
normalization with soft radial dampening (see `LayerDampening` in ``grce.py``).
Instead of forcing activations onto a unit-RMS shell, LD only attenuates large
magnitudes using a learned sharpness parameter log_k:

	k = torch.exp(self.log_k)
	denom = 1.0 + F.softplus(k * (r - 1.0)) / k

This softly constrains the signal to the interior of the unit ball, rather than
projecting it onto the unit sphere. It reduces noise from small signals by
preserving them as they are, prevents runaway growth, and allows the model to
adapt the strength of injected bias differently for attention and MLP paths with
minimal additional parameters.

Let's call the recurrent GRCE signal G, the updated recurrent signal G'. Let the
sampled signal from the input to transformer layer i be S_i, and let the per-layer bias
vectors, added to both LN()-outputs in the transformer block, be B_i.

The model embedding dimension is n_embd. The width of the recurrent GRCE channel
is n_grce, and the width of the recurrent XCTX channel is n_xctx. Note that usually
n_grce < n_embd < n_xctx.

A "classical" (GPT-2 design) transformer block is simply this:
Let Up4xE_i() be a per-layer learned linear from n_embd to 4*n_embd
Let Dn4xE_i() be a per-layer learned linear from 4*n_embd to n_embd
  H_i := MultiHeadAtt_i(LN(S_i))
  T_i := S_i + H_i
  R_i := Dn4xE(GELU(Up4xE_i(LN(T_i))))
  S_{i+1} := T_i + R_i

Now with GRCE and/or XCTX bias added:
  H_i := MultiHeadAtt_i(LN(S_i)+B_i)
  T_i := S_i + H_i
  R_i := Dn4xE(GELU(Up4xE_i(LN(T_i)+B_i)))
  S_{i+1} := T_i + R_i

The (low-dimensional) GRCE channel (G -> G'):
Let G2E_i() be a per-layer learned linear from n_grce to n_embd.
Let E2G_i() be a per-layer learned linear from n_embd to n_grce.
Let Up4xG() be a learned linear from n_grce to 4*n_grce
Let Dn4xG() be a learned linear from 4*n_grce to n_grce
  Bias injection based on the signal from the previous position(s) via recurrent input G, create bias
  values B_i for the n_layer layers, add with bias from XCTX if both GRCE and XCTX are enabled.
    B_i := G2E_i(LN(G))
  For each transformer layer i at this position and thus for each sampled vector S_i:
    Z_i := E2G_i(LN(S_i))
  Then the shared mixing stage, combining the recurrent input signal G with the per-layer values:
    M := LN(dropout(G + Z_0 + Z_1 + ... + Z_{n_layers-1}))
  Then re-mixing M with an MLP into a new recurrent vector G'
    G' := LD(G + dropout(Dn4xG(GELU(Up4xG(M)))), with_gain=False)

The GRCE architecture is almost identical to a block of the transformer stack,
except that it has the transformer stack itself in its first half, instead of
the attention mechanism that we find in the first half of each block of the
transformer stack. Note that via the path B_i -> Z_j (with i<j) through the
transformer, the GRCE path can access compute resources inside the transformer
stack, and thus only one shared MLP layer is ever needed in the GRCE data path
itself, for remixing the mixed G and Z_i signals from different layers into an
updated single recurrent state vector G'.

The (high-dimensional) XCTX channel (X -> X'):
Let u := min(n_embd // 2, n_xctx // 2, max(n_embd // 4, n_xctx // n_layer)), an intermediate dimension <n_embd and <n_xctx
Let E2U_i() be a per-layer learned linear from n_embd to u.
Let U2X_i() be a per-layer learned linear from u to n_xctx.
Let X2U_i() be a per-layer learned linear from n_xctx to u.
Let U2E_i() be a per-layer learned linear from u to n_embd.
Let DnX() be a learned linear from n_xctx to n_xctx/2.
Let UpX() be a learned linear from n_xctx/2 to n_xctx.
Let W() be a learned linear from n_xctx to n_xctx.
Let center() be the "center" function: center(Y) = Y - ones()*mean(Y)
  Bias injection based on the signal from the previous position via recurrent input X:
    B_i := U2E_i(LN(X2U_i(X)))
  For each transformer layer i at this position and thus for each sampled vector S_i:
    Z_i := U2X_i(LN(E2U_i(center(S_i))))
  Then the shared mixing stage, combining the recurrent input signal X with the per-layer values:
    M := LN(DnX(dropout(X + Z_0 + Z_1 + ... + Z_{n_layers-1})))
  Un-squeeze and convert back into X-space with MLP
    Y := W(GELU(UpX(M)))
  Updating the original recurrent X input (not M) with Y, but without the
  mean component, then rescale the recurrent signal with RMSNorm (not LN):
    X' := RMSNorm(X + center(dropout(Y)))

The XCTX architecture uses a similar bias-sample-mix-remix architecture as
GRCE, but shapes noise, manages dimensionality of updates, and incorporates
other changes, such as using a direction-preserving norm (RMSNorm instead of
LN) in the recurrent path, that makes XCTX better suited to perform short-term
memory and working memory functions, instead of the position-by-position
state-machine-like functionalities that the GRCE channel can implement better
and more easily.

**Note:** To obtain true left-to-right evaluation, the Transformer core must be
using an **incremental, KV-cached forward** architecture. Each time step must
run the *full layer stack for a single token*, appending that token’s K/V to
per-layer caches and attending only against cached past keys/values. (In
`encode` blocks we run the transformer with simple un-masked attention, so
we must not use a KV-cached architecture in the case of `encode` blocks.)

### Future/Next Experiments

We propose a “Radial Gated Mixer” (RGM) for the recurrent update. Right now every
partial sum inside GRCE/XCTX passes through Layer Dampening, so the model has to
keep rebuilding old signals (G' = LD(G + delta)). In RGM we add a per-feature gate
alpha and define

      G' = alpha * G + dampen(delta)

where dampen(delta) uses the same soft radial shrinkage to keep the resulting
G' inside the unit ball. Redundant or oversized delta terms are softened or even
eliminated before they modify the state, while the residual alpha * G carries
useful information forward without extra amplification.

### Rationale for the recurrent channels, additional thoughts, and predicted behavior

The vector of concatenated S_i values for a position already encodes the entire
context for the next position. The position has to evaluate that context as part
of predicting that token. Experiments show that we can disable gradient
propagation at this interface entirely (--detach-span 1) and observe
almost no difference in how well and/or quickly the network can learn the GRCE
and XCTX functionality. This demonstrates that all the context information is
already present in the set of S_i vectors, we only need to learn how to sample
and extract that already-present information from that vector using the GRCE
and XCTX sample-mix-remix pipelines.

That has tremendous implications! It basically means we have an easy pathway to
learning a recurrent large language model without having to learn a deep and
complex recurrent function: we instead just augment the transformer with two
simple mechanisms to "shout" important information into the future, that the
future will "see" without any need to explicitly query it. And then we use
dropout-style training scenarios that force optimization to build redundant
structures with GRCE and XCTX, that can "help out" when we drop out attention
for a position, until we can disable attention entirely and still get reasonable
results, at least on short sequences, with GRCE and XCTX as the only path that
allows flow of information between transformer stacks.

The main purpose of this is (1) generally higher stability by creating a
redundant path for information, for all the cases where attention "glitches",
and (2) models that can be debugged more easily, even on a very low level.
The GRCE and XCTX channels provide model stability wrt to the current "role"
and other information. Whenever a model fails to "stay in character", or
"drift out of character", this will be manifest in the GRCE and XCTX signals!
So it will be possible to just sample those signals, inject them into a
new model instance, and present the model with <|!:> (dump context begin) so it
can verbalize its context. This mode/information can then even be
used to automatically learn certain GRCE embeddings, once the model has been
trained to extract and verbalize the right information. (In reality this may
very well turn out to be simple in some cases and very much not so in others... ;)

The GRCE channel is low-dimension/low-bandwidth and we expect it to learn to
encode and send forward properties like the "current role" that may be
stable without "drift" for a certain time, then maybe change sharply whenever
the role changes, and we also expect it to learn to encode and send forward
properties that are only useful for the immediate next token or maybe word,
such as grammatical context for the next token or word. The remixing stage of
the GRCE channel is expected to quickly saturate the channel, so that, for the
most part, only information that is actively pushed forward by each position is
going to survive. In short: we expect the GRCE channel to implement various
forms of state machines.

For XCTX channel on the other hand we first squeeze the M vector into a n_xctx/2
dimensional vector space before the MLP. Resampling that by projecting back to
n_xctx followed by GELU is exactly enough to fully GELU-decompose the n_xctx/2
wide channel. There is no down-projection after the GELU layer, we stay in
n_xctx, just perform a single linear from n_xctx to n_xctx, and then use a
direction-preserving norm for the recurrent path, so no noise is introduced
into the channel that is not intentional signal interaction, because we can
always learn n_xctx (almost) linearly independent row/columns in W, whenever
independent channels in the XCTX recurrent path are desired. This path is meant
to be able to accumulate information over a span of positions and just carry them
forward in time for as long as bandwidth is available in the path, with new
information cleanly overwriting or adding to older information, without adding
any "architectural noise" into the critical (recurrent) path in the process.


## PyTorch Model

### TransformerStackGrid

We create the following TransformerStackGrid(nn.Module) class:

	stackgrid = TransformerStackGrid(settings)
	y, s_out, kv_out = stackgrid.forward(x,
			bias_list_in=[], kv_cache_list_in=[],
			qh_query_callback=None, mode="decode")

Note: We use rows for the batch dimension (often B) and cols for the
time dimension (often T). This is intentional: a full batch may be
assembled from multiple smaller grids, in which case individual grids may
have rows < B and/or cols < T.

The tensor 'x' has size [rows, cols, n_embd] and stack.forward() evaluates
a whole rows*cols grid of transformer stacks, with 'rows' = number of
parallel running sequences (= "batch size") and 'cols' = positions in
time-domain (= "block size"). The main output 'y' has the same size
as 'x'. So the "stack" in "StackGrid" really is only the stack of transformer
blocks, without the embeddings generating the n_embd-sized input vectors in 'x'
and the decoder interpreting the n_embd-sized output vectors in 'y'.

The (possibly empty) list 'bias_list_in' contains tensors of maximum size
[rows, <=cols, <=n_layers, n_embd]. (Each tensor in a list can have a different
size in its second of third dimension, as long as the 2nd dim is <=cols and the
third dimension is <=n-layers. The tensors contain the 'biases' added to the
two n_embd-sized LN() output vectors in each block in the stack, for the first
<=cols columns in the grid, and the first <=n_layers. (usually <=cols is simply
either one or cols, and <=n_layers is usually either one or n_layer.)

The argument 'kv_cache_list_in' is a list of lists of 2-tuples. The first
list-dimension is simply the source and the second dimension is the layer.
Each 2-tuple is "per-layer k/v-cache" and contains two tensors of the same
size: [rows, n_kv, n_heads, head_dim], with n_embd = n_heads * head_dim, and
with n_kv as the arbitrary number of entries in the given cache. (Usually
n_kv is simply the number of columns of the grid that produced this kv-cache.
The output 'kv_out' is a single such n_layers-sized list of 2-tuples.

The callback 'qh_query_callback,' basically implements keyed external memory:

	M, S, T = qh_query_callback(Q, layer)

Where Q and T have size [rows, cols, n_heads, head_dim], and M and S have size
[rows, cols, n_heads].  M, S, and T contain the values needed to combine the
external contribution to H from qh_query_callback() with the contributions from
the kv_caches as well as attention within the transformergrid: M_k is the
max_i(x_i=Q*K_i^T) value for the row/col/head specified in k. S_k is the
sum_j(exp(x_j - M_k)).  And T_k is the H value for the external contribution
only: sum_i(V_i*exp(x_i - M_k)) / S_k.

With mode="decode" we perform standard masked causal self-attention and train
the stack to predict the next token. With mode="reverse" we apply the
transpose of that mask (each token attends to future positions but not the
past), swap the x/y roles so the model predicts the *previous* token, and add
the `[|predict-prev|]` embedding to every column instead of `[|predict-next|]`.
Mode="encode" allows every position to attend to every other position (only
the final column is supervised) and mode="noattn" uses purely self-attention.
External KV caches and `qh_query_callback` are available in every mode.

The output 's_out' is a list of size n_layers+1, containing tensors of size
[rows, cols, n_embd], with the sampled inputs and outputs to all transformer
blocks in the grid.  Note that the first element in 's_out' is simply the input
'x' and the last element is simply the "transformed" output 'y'.

### Optimized tensor memory layout (not currently implemented that way)

The tensor dimensions used in the API are all using 'rows' as first dimension
and 'cols' as second dimension, because that is cleaner from an API
point-of-vies. For example:
	[rows, cols, n_embd]
	[rows, cols, n_layers, n_embd]
	[rows, cols, n_heads, head_dim]

However, if there's an iteration, then code iterates over 'cols' first, so
that should be the first dimension in memory. Thus allocate tensors [cols, rows, ...]
and then immediately re-shape them into the "API form".

### GRCE and XCTX shims

With GRCE and/or XCTX enabled we cannot create an entire multi-column grid
at once, because the recurrent GRCE/XCTX channels force us to evaluate the
transformers sequentially, one time-position at once.

We create pairs of GRCE and XCTX "bias" shims with almost identical interfaces:

	grce = TransformerGRCE(settings)
	xctx = TransformerXCTX(settings)

	b_out = grce.bias_forward(grce_in)
	b_out = xctx.bias_forward(xctx_in)

The 'grce_in' and 'xctx_in' signals are the recurrent GRCE or XCTX inputs.
Their size is [rows, n_grce] or [rows, n_xctx]. The 'b_out' outputs can be
inserted directly in the 'bias_list_in' argument of stackgrid.forward().
These 'b_out' outputs have size [rows, 1, n_layers, n_embd].

	grce_out = grce.sample_forward(grce_in, S_in, detach_samples=False)
	xctx_out = xctx.sample_forward(xctx_in, S_in, detach_samples=False)

These calculate the recurrent GRCE/XCTX outputs based on the recurrent input
and the sampled values from the stack in 'S_in'. (Note that tensors in the
'S_in' list may have a 'cols' dimension > 1, but for convenience these two
functions are only ever using the _last_ entry in the 'cols' dimension. This
means only S_in[:][:, -1, i, :] is ever read by sample_forward().)

We can detach the recurrent path in "the middle" of a position, by detaching
the arguments to .sample_forward():

	detached_grce_out = grce.sample_forward(grce_in.detach(), S_in, detach_samples=True)
	detached_xctx_out = xctx.sample_forward(xctx_in.detach(), S_in, detach_samples=True)

When this is done for all positions, the recurrence collapses and maximum
path-length for backprop is almost unchanged by the addition of the recurrent
GRCE and XCTX paths.

In summary: bias_forward() always consumes the recurrent state from the
previous position; sample_forward() produces the recurrent state for the next
position.

### TransformerStackColumn and TransformerStackSequence

TransformerStackColumn simply is a grid with cols=1, and added GRCE and XCTX
bias and sample shims.

TransformerStackSequence is a 2-D (rows x cols) sequence of such columns,
resembling a StackGrid, but with added GRCE and XCTX channels:

	seq = TransformerStackSequence(settings)
	y, grce_out, xctx_out, kv_out = seq.forward(x, grce_in, xctx_in,
			bias_list_in=[], kv_cache_list_in=[], qh_query_callback=None,
			mode="forward", detach_internal_kv_cache=False,
			detach_samples_span=0, detach_grce_span=0, detach_xctx_span=0,
			think_step_index=None, think_step_count=None)

With {grce,xctx}_{in,out} of size [rows, n_{grce,xctx}]. (So {grce,xctx}_out
are the final recurrent states after the last column.)

Columns are evaluated strictly left-to-right, and GRCE/XCTX state updates from
column t are visible only to column t+1. When the layout requests explicit
thinking (e.g. `f2x`, `f3x`, `f4x`, or `t...`) we duplicate the input tokens so
each think-step occupies its own column and pass `think_step_index` /`think_step_count`
(shape [cols]) into `seq.forward`. Only the final column in the span is
supervised; the intermediate think-columns run the full stack (including
GRCE/XCTX sampling) but their targets are masked out. Additionally we loop the
LayerNorm-normalized output of each intermediate column back into the next
column’s input within the same span, so later think steps see both the original
embedding and the refined residual from previous stacks. Thinking is available
only in forward mode; using `t` instead of `f` simply records its losses under
the dedicated `think` metric while sharing the same forward compute path.

With GRCE and XCTX disabled (n_grce=0 and n_xctx=0), TransformerStackSequence
is functionally equivalent to evaluating a TransformerStackGrid with the same
inputs.

The values from 'bias_list_in' are applied per column: biases for column t are
applied to TransformerStackColumn[t] in the same way as in TransformerStackGrid.

We maintain an internal kv_cache, as described in "Management and balancing of
k/v-caches in sequences" below, which we return as kv_out.

When mode="noattn" we skip applying the internal kv_cache. Thus in "noattn"
mode the recurrent channels are the only way of passing information forward
within the sequence. (Note that we still apply self-attention and we still
attend to 'kv_cache_list_in' and 'qh_query_callback'.)

When mode is "encode", "decode", or "reverse", then a single large internal stack grid
is created that covers all the positions in the sequence. In this case we
call .bias_forward() only once for the first position of the sequence, and
only inject that bias into the first position. After running .forward()
for the grid we call .sample_forward() for each channel and position to
calculate the values for 'grce_out' and 'xctx_out'.

When detach_*_span>0 then the recurrent path or S-sampling is detached every
detach_span positions. So detach_samples_span=1 will detach S-sampling at every
position, but still allow full backprop on the recurrent XCTX and GRCE signals.

### Management and balancing of k/v-caches in sequences

There are two mechanisms to manage the internal kv-cache of a sequence:

1) As list[:] of list[n_layers] of 2-tuples of tensor[rows, n_kv, n_heads, head_dim]

Each time we receive a new kv_out (list[n_layers] of 2-tuples of tensors)
we simply append that kv_out to our kv_cache_list, which we pass via the
kv_cache_list_in argument to .forward() of a grids and sequences.

Having a large such list, each with a small 'n_kv' inner dimension is
inefficient. So we call kv_cache_list_balance() on our kv_cache_list
after appending one or more additional kv_out to it, and before using
it as kv_cache_list_in in a .forward() call the next time.

kv_cache_list_balance() utilizes a helper function kv_cache_list_merge()
that consumes a kv_cache_list_in-style list of lists of 2-tuples of tensors,
and re-arranges that into a single list[n_layers] of 2-tuples of tensors.

At the end of the sequence we then use kv_cache_list_merge() to convert
the final state of kv_cache_list into the kv_out return value.

Another helper kv_cache_list_detach() can be used to .detach() all
tensors in a kv_cache_list. (This is not done by default, but can
be done by the caller. See also batch composition below.)

2) As .detach()-ed k/v copies in two pre-allocated tensor[rows, cols, n_heads, head_dim]

When in detach_internal_kv_cache=True mode we simply pre-allocate kv_out.

For each position we then create a list[n_layers] of 2-tuples of tensors[:,:pos,:,:]
kv_cache that we can pass in kv_cache_list_in to .forward().

When we receive a kv_out we simply store a .detach()'d copy of it in a slice of
our pre-allocated kv_out tensor pair.

Both of those modes are available in evaluation and training! The kv-detached cache
is NOT just an inference-only optimization. Instead, we can use it to speed
up training for sequences with GRCE/XCTX enabled. In those cases, with detached
kv-caches for some instances of the model, we simply rely on the other
instances in the training batch to learn useful k/v values, which then can be
used as detached values when training the recurrent channel.

### Training and test corpus window management

We determine the per-step number of tokens by creating the sum of the tokens
consumed by each micro-batch. Then we multiply that number by STEPS and this
is the size of the window we pull for each cycle.

For each step we then pick a random continuous sub-window of the calculated sum.
The micro-batches can only use that sub-window. Each micro-batch now picks a
random sub-window within the per-step window. Each row then picks a random
sub-window within the per-microbatch window.

### Composition of training and evaluation batches

Training and evaluation batch layouts are declared using the 'Mini-language for
batch layouts', as described in the next section.

These batch layouts are composed from the following sequence types:
- "encode"
- "decode"
- "forward"
- "noattn"
- "reverse"

There's GRCE and XCTX paths going through the entire flow, but "encode",
"decode", and "reverse" generate the GRCE and XCTX signals "blindly",
without means of "sensing" the GRCE or XCTX signals via bias injection.

Reverse blocks automatically mirror the decode input/output streams: every
column receives the `[|predict-prev|]` embedding, consumes the token that
follows the target in the corpus, and learns to emit the previous token while
the attention mask is flipped. Decode/forward/noattn continue to receive
`[|predict-next|]` and predict the next token instead.

Note that for the "encode" sequence we must only use the prediction from the
very last position, that predicts the next token after the encode block
input.

We report 4 loss numbers when evaluating the model: "target" = the actual
optimization target, "encode" = loss only based on the last column of the
encode block, "decode" = loss based on all columns of the decode (and
reverse) blocks, and likewise for "forward" and "noattn".


## Mini-language for batch layouts

We define a mini-language for (training and evaluating) batch layouts:

	12[16e=16d]+4[48f]+1[8f=8d=8f]

This example means we first have a 12-row-wide stack of the following
sequences: a 16-column-long "encode" sequence followed by a 16-column-long
"decode" sequence, with the outputs of the first sequence connected to the
inputs of the second sequence.

Next we have a single 4-row by 48-column "forward" sequence. Finally there's a
single-row sequence with 8 columns of "forward", followed by 8 columns of
"decode", and another 8 columns of "forward".

We remove all --rows-*, --cols-*, --split-* CLI options, and --batch-layout,
and replace it all by a single --layout STR option, that accepts the above
syntax. A warning is generated when the number of rows exceeds --batch-size
or the number of cols in any row exceeds --n-pos/--block-size.

There's more syntax to introduce randomness and dynamically adjust a layout
to a given --batch-size and --n-pos/--block-size. Consider this layout:

	2[*d]+2[*f]+*[*1-2e=*1-4d=*1-4f=*1-2n]

So we have 2 rows by block-size cols of "decode", then 2 by block_size "forward",
then batch_size-4 rows of an encode-decode-forward-noattn pattern, with the columns
assigned as follows: first a random number in the range of 1-2 is allocated for
"encode"; then numbers in the range 1-4 for the "decode" and "forward" sequences;
and finally a number in the range 1-2 for "noattn".

If the available --n-pos/--block-size is smaller than the resulting total
sequence length, we randomly select sub-blocks that are still over their lower
bound, and decrement them, until block_size is reached, or each segment is at its
lower bound.

If the available block_size is larger, we step-by-step expand the segments marked
with an * using the following method: we weight the segments according to their
current size and select a random segment to increment in size using this weighting.
This way relative size differences are not evened out by the expansion process.

The syntax *5 is just short for *5-5. And just * is a special form that means
allocate a baseline of 0, but participate in expansion with a weight of at
least 1, even when the current size is zero. Finally, +N-M has a similar
meaning as *N-M, but the segment will not grow beyond M. The syntax +M is just
short for +1-M; and just + is a special form that is similar to * except
it participates in expansion with a constant weight of 1 regardless of
current size. These prefixes work exactly the same way for rows (outside of
[...]) and cols (inside of [...]).

Instead of an integer one can also use a fraction A/B. In this case this
represents (A * (batch-size or block-size)) // B.

In addition to that we define a simple pre-processing language, using '(', '|',
and ')' to express alternatives for random choices. This is a pure text-based
pre-processor. So the following is valid syntax:

	*[*e(=|]+*[)*d]    ... for either  *[*e=*d]  or  *[*e]+*[*d]

Batch layouts are passed to grce.py with --layout and --log-step-layout-times
prints a message with concrete layout and training time for each training step.

The top-level elements can be separated by , instead of +. A , denotes
the boundary between micro-batches. Everything between two commas must
fit onto the GPU and we run forward an backward on all of it. But instead
of running optimize we then run forward and backward for the next micro-batch,
accumulating gradients. So for example:

	128[64f](,1[1024f]|||)

This creates batches of 128x64, but in 25% of the batches an additional
micro-batch of size 1x1024 is added and included in that optimize step.

Modifiers for the [...] block can be inserted directly before the [ char:

	k   enable --detach-kv-cache for the [...] block
	sN  enable --detach-span N for the [...] block ('s' is short for 's1')
	c   enable --no-detach-ctx for the [...] block
	T   freeze recurrent parameters so only the transformer stack learns
	C   freeze transformer parameters so only the context/recurrent channels learn
	P   suppress positional encodings within this block
	H   don't add the loss values from this block to the typed metrics, only {test,train}_loss

In this context "transformer parameters" include everything that shapes the
encode/decode (E/D) stack, while "recurrent parameters" cover the GRCE/XCTX
channels, their samplers, mixers, and bias injectors.

This means 'sc[*f]' has a deep path along the context, but we never backprop
into the transformer. 'ks3[*f]' on the other hand will backprop a few columns
of the transformer, but it will not visit later positions via the attn mechanism,
because of the detached kv-cache.

Instead of e d f n r one can also use E D F N R as sequence type. In that case
the recurrent outputs of the block remain unused. The layout [*d=*d] generates
XCTX and GRCE signals "blindly" in the first decode block, and then they are being
passed to the first row of the second block, which receives biases from that
recurrent context. (backprop for [*d=*d] takes about twice as long as [*d].)
The layout [*D=*d] on the other hand is functionally equivalent to [*d].

Lowercase `r` defines a "reverse" sequence: it behaves like `d` (decode)
but uses the transpose of the standard causal mask, so each position attends
to future tokens instead of the past. Uppercase `R` works the same way but
disables recurrent/context updates, mirroring how `E/D/F/N` behave.

Appending `p`/`P` to a mode (e.g. `16ep` or `4Rp`) suppresses positional
embeddings inside that block. This trains the model to rely on contextual
state for indexing rather than absolute positions; the uppercase/lowercase
rules still apply in addition to the positional suppression.

Likewise `h`/`H` (hide typed losses) can be appended to a mode to suppress
adding those losses to the typed metrics. For example *[16e=*th2x=*t4x]
will train for 2x and 4x thinking, but only the 4x thinking losses are
reported in the "think" metric.

Appending `2x`, `3x`, or `4x` to a mode enables 2x/3x/4x "thinking" (see below).
When the letter `t` is used instead of `f`, loss from thinking is recorded
in the "think" category rather than "forward".

We also allow > instead of = for chaining sequences inside of a [...] block.
The difference is that with > we drop the entire k/v-history at this point,
so only the recurrent channels can pass information along that barrier.


## Thinking Models -- (this is work in progress)

Standard transformers have a structural limitation: attention only connects
tokens across time *within the same layer*. Information computed in higher
layers at position t cannot directly influence lower layers at position t+1.
Any cross-layer temporal influence must be re-encoded into the token stream and
reprocessed bottom-up, which is indirect and lossy. The current state of the
art for mitigating this is Chain-of-Thought (CoT), which trains the model to
emit intermediate reasoning steps. However, CoT is not an architectural feature
of large language models; it is purely a learned behavioral pattern and does
not introduce explicit internal state or compute control.

GRCE and XCTX already remove this limitation without introducing any notion of
“thinking”. By sampling activations from all layers at a position, mixing them,
and injecting the result into any layer of the next position(s), they allow
information to cross layer boundaries across time explicitly. The entire
context discovered at one position becomes available to subsequent positions in
a layer-agnostic way.  This can free attention heads to focus on retrieval,
alignment, or comparison, rather than on carrying state forward, and it also
enables the *next position* to rebroadcast that information from a lower layer
if additional compute or restructuring is useful.

Thinking is therefore not the same as reasoning. Reasoning is the sequence of
transformations the model applies to information, as it summarizes it into more
new tokens. Thinking is the allocation of time and compute that determines how
many such transformations can be applied to a position before the model must
commit to a prediction.

There are two complementary ways to allocate thinking time. One is explicit and
fixed: duplicate tokens and positions and annotate them with `think:n/k`,
telling the model exactly how many think steps exist and which one it is
currently in. The other is adaptive: guarantee availability via `think-avail`
and let the model request more time by predicting the `<|think|>` token. In
both cases, the crucial point is that the model knows *in advance* whether at
least one more time slice is available, so it can safely postpone commitment.

(However, at the moment only the explicit mode is supported. The adaptive
allocation of think-time is still future work.)

Because of GRCE and XCTX, multiple passes over the same input position are not
redundant. Each additional stack runs with updated recurrent state, so later
think steps do not simply repeat earlier computations. GRCE provides
low-bandwidth control over phase and strategy, while XCTX carries
high-bandwidth accumulated context forward. This turns repeated stacks into a
genuine multi-step process rather than a redundant loop.

XCTX in particular enables cross-layer interaction across time. Signals sampled
from different layers are mixed and remixed before updating the recurrent
state, so an update to the XCTX vector can depend on the *joint presence* of
signals from multiple layers. As a result, thinking longer is not about doing
the same work twice, but about enabling conditional, staged computation whose
effects can propagate far forward in the sequence. One especially interesting
consequence is that later positions — far downstream — may see reduced loss
because they can rely on information that was explicitly stabilized and refined
during earlier thinking steps, rather than having to reconstruct it again
through attention alone.

In addition to the GRCE and XCTX data paths we also adopt the idea of looping
transformers: Within a think-span of N transformer instantiations for the
same position we take the LayerNorm of the output of each transformer but the
last in the span and add that to the input of the next transformer.

As thinking requires a recurrent data path, it is only available in "forward"
mode. If "t" is used instead of "f" in the layout string then the losses are
recorded under the "think" metric instead of "forward".


## 2-D RoPE on a Torus (future work)

We extend RoPE from a single circular phase to two orthogonal angles (θ₀, θ₁) on S¹×S¹. Each
attention head splits its Q/K subspace into rotary pairs and applies both rotations, so
dimensionality stays unchanged and relative phases still determine the attention weights. The
primary axis θ₀ advances along the base text while θ₁ advances whenever we branch off into a
lateral chain; holding θ₀ fixed at a branch point and walking along θ₁ lets us “step off” the text
without forgetting where the branch started.

During pretraining on ordinary 1-D text we can draw a random positive-quadrant direction vector
(α, β) and treat each fragment as moving along αθ₀ + βθ₁. Because RoPE depends only on relative
angles, this acts as positional augmentation without privileging a single axis. Isolation of
segments still relies on standard attention masking; random phases alone do not fence them off.

The learned direction embeddings [|rope:0|] / [|rope:1|] encode the current trajectory
so downstream modules know whether we are moving along the text axis, a branch axis, or a mixture.
Straight text sets α≈1, β≈0; a lateral chain sets α≈0, β≈1; diagonal walks are also possible.
Depending on the task we can dedicate half the rotary frequencies to θ₀ and half to θ₁ for clean
separability, or linearly mix both angles per frequency to capture interactions between text
position and branch depth.

This torus inductive bias is well-suited to “text plus lateral reasoning” structures. Extending
and generalizing to an N-torus would be straightforward, but we only need a 2-torus in our
application, with θ₀ for the "external" text and θ₁ for the "internal" chain of thought.

  it's a token and not a non-token embedding, because we might
  want to add it to training data in order to teach the model

  to only do that, when [|think-avail|] is present on the input,
  or the model is inside a <|@:> ... <:@|> block.

  always be <|p{N-1}|> ... <|p0|>. this means injecting such a process-sequence
  will effectively free the model from spending any compute on predicting the
  immediate next token for the next N positions, and is instead free to use its
  attention heads and compute to re-structure what it knows and make that
  re-structured information available to the later positions in the sequence,
  in whatever way of form turns out to be useful within the training corpus.
  In a transformer without recurrent path this exercise would be pointless.
  But with the added recurrent GRCE and XCTX channels, just adding those
  process-tokens is already enough to enable a simple first mode of "additional
  thinking time". (We usually add such a sequence in training in a special
  training mode, where we add them at random positions in the corpus, always
  between a punctuation mark (!?:;,. or ") and a whitespace that follows it.
