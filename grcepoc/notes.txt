# GPT+GRCE+XCTX Reference Specs

This is the hand-written reference spec, the definitive source of information
about the intended design behavior, mostly directed at AI agents (= OpenAI Codex).


## GRCE and XCTX data path spec -- (updated; implementation not up-to-date)

GRCE and XCTX both sample the n_layer input vectors to the transformer blocks in the
stack at a position, mix with a recurrent GRCE or XCTX signal (G or X), remix, and
update the recurrent signal (G' and X'), and then inject the context information into the
transformer layers at later positions. Each have a per-layer sample stage, a shared
mix and remix stage, and then per-layer bias-injection stage in the next position.

Let's call the recurrent GRCE signal G, the updated recurrent signal G'. Let the
sampled signal from the input to transformer layer i be S_i, and let the per-layer bias
vectors, added to the transformer inputs after sampling S_i, be B_i.

The model embedding dimension is n_embd. The width of the recurrent GRCE channel
is n_grce, and the width of the recurrent XCTX channel is n_xctx. Note that usually
n_grce < n_embd < n_xctx. (n_xctx must be a multiple of n_layers.)

A transformer block is simply this (GPT-2 design, with GRCE and XCTX bias added):
Let Up4xE_i() be a per-layer learned linear from n_embd to 4*n_embd
Let Dn4xE_i() be a per-layer learned linear from 4*n_embd to n_embd
  Z_i := S_i [+ GRCE B_i bias signal, if present] [+ XCTX B_i bias signal, if present]
  H_i := MultiHeadAtt_i(LN(Z_i))
  T_i := Z_i + H_i
  R_i := ReLU(Up4xE_i(LN(T_i)))
  S_{i+1} := T_i + Dn4xE(R_i)

The (low-dimensional) GRCE channel (G -> G'):
Let G2E_i() be a per-layer learned linear from n_grce to n_embd.
Let E2G_i() be a per-layer learned linear from n_embd to n_grce.
Let Up4xG() be a learned linear from n_grce to 4*n_grce
Let Dn4xG() be a learned linear from 4*n_grce to n_grce
  Bias injection based on the signal from the previous position(s) via recurrent input G, create bias
  values B_i for the n_layer layers, to be added to block inputs *after* sampling the vectors S_i:
    B_i := G2E_i(LN(G))
  For each transformer layer i at this position and thus for each sampled vector S_i:
    V_i := E2G_i(LN(S_i))
  Then the shared mixing stage, combining the recurrent input signal G with the per-layer values:
    M := LN(G + V_0 + V_1 + ... + V_{n_layers-1})
  Then re-mixing M with an MLP into a new recurrent vector G'
    G' := LN(M + Dn4xG(ReLU(Up4xG(M))))

The GRCE architecture is almost identical to a block of the transformer stack,
except that it has the transformer stack itself in its first half, instead of
the attention mechanism that we find in the first half of each block of the
transformer stack. Note that via the path B_i -> V_j (with i<j) thru the
transformer, the GRCE path can access compute resources inside the transformer
stack, and thus only one shared MLP layer is ever needed in the GRCE data path
itself, for remixing the mixed G and V_i signals from different layers into an
updated single recurrent state vector G'.

The (high-dimensional) XCTX channel (X -> X'):
Let u := min(n_embd // 2, n_xctx // 2, max(n_embd // 4, n_xctx // n_layer)), an intermediate dimension <n_embd and <n_xctx
Let E2U_i() be a per-layer learned linear from n_embd to u.
Let U2X_i() be a per-layer learned linear from u to n_xctx.
Let X2U_i() be a per-layer learned linear from n_xctx to u.
Let U2E_i() be a per-layer learned linear from u to n_embd.
Let DnX() be a learned linear from n_xctx to n_xctx/2.
Let UpX() be a learned linear from n_xctx/2 to n_xctx.
Let W() be a learned linear from n_xctx to n_xctx.
  Bias injection based on the signal from the previous position via recurrent input G, create bias
  values B_i for the n_layer layers, to be added to block inputs *after* sampling the vectors S_i:
    B_i := U2E_i(LN(X2U_i(X)))
  For each transformer layer i at this position and thus for each sampled vector S_i:
    V_i := U2X_i(LN(E2U_i(S_i)))
  Then the shared mixing stage, combining the recurrent input signal G with the per-layer values:
    M := LN(DnX(X + V_0 + V_1 + ... + V_{n_layers-1}))
  Then re-mixing the original recurrent X input (not M) with an MLP into the new
  recurrent vector X'; with RMSNorm (not LN, for better stability in recurrent path):
    X' := RMSNorm(X + W(ReLU(UpX(M))))

The XCTX architecture uses a similar bias-sample-mix-remix architecture as
GRCE, but shapes noise, manages dimensionality of updates, and incorporates
other changes, such as using a direction-preserving norm (RMSNorm instead of
LN) in the recurrent path, that makes XCTX better suited to perform short-term
memory and working memory functions, instead of the position-by-position
state-machine like functionalities that the GRCE channel can implement better
and more easily.

**Note:** To obtain true left-to-right evaluation, the Transformer core must be
using an **incremental, KV-cached forward** architecture. Each time step must
run the *full layer stack for a single token*, appending that token’s K/V to
per-layer caches and attending only against cached past keys/values. (In
`encode` blocks we run the transformer with simple un-masked attention, so
we must not use a KV-cached architecture in the case of `encode` blocks.)

In `encode` blocks (see below) the GRCE channel is disabed. Only the last
position in an `encode` block has the GRCE sampler and shared path, to generate
a GRCE output from the last position of the encoder only. The recurrent XCTX
channel however is present for all positions of the encoder, but without the
bias injection networks. So one could say in `encode` mode each transformer
position is "blindly" injecting information into the shared forward-projecting
XCTX data path. `recode` rows (see below) are used to train such encoders to
produce pairs of GRCE and XCTX outputs that that decoders can consume.


## Rationale for the recurrent channels, additional thoughts, and predicted behavior

The vector of concatenated S_i values for a position already encodes the entire
context for the next position. The position has to evaluate that context as part
of predicting that token. Experiments show that we can disable grandient
propagation at this interface entirely (--detach-span 1) and observe
almost no difference in how well and/or quickly the network can learn the GRCE
and XCTX functionality. This demonstrates that all the context information is
already present in the set of S_i vectors, we only need to learn how to sample
and extract that already-present information from that vector using the GRCE
and XCTX sample-mix-remix pipelines.

That has trememdous implications! It basically means we have an easy pathway to
learning a recurrent large language model without having to learn a deep and
complex recurrent function: we instead just augment the transformer with two
simple mechanisms to "shout" important information into the future, that the
future will "see" without any need to explicitly query it. And then we use
dropout-style training scenarios that force optimization to build redundant
structures with GRCE and XCTX, that can "help out" when we drop out attention
for a position, until we can disable attention entirely and still get resonable
results, at least on short sequences, with GRCE and XCTX as the only path that
allows flow of information between transformer stacks.

The main purpose of this is (1) generally higher stability by creating a
redundant path for information, for all the cases where attention "glitches",
and (2) models that can be debugged more easily, even on a very low level.
The GRCE and XCTX channels provide model stability wrt to the current "role"
and other information. Whenever a model fails to "stay in character", or
"drift out of character", this will be manifest in the GRCE and XCTX signals!
So it will be possible to just sample those signals, and inject them into a
new model instance and present the model with <|!:> (dump context begin) and
the model can verbalize it's context. This mode/information can then even be
used to automatically learn certain GRCE embeddings, once the model has been
trained to extract and verbalize the right information. (In reality this may
very well turn out to be simple in some cases and very much not so in others... ;)

The GRCE channel is low-dimension/low-bandwith and we expect it to learn to
encode and send forward properties like the "current role" that may be
stable without "drift" for a certain time, then maybe change sharply whenver
the role changes, and we also expect it to learn to encode and send forward
properties that are only useful for the immediate next token or maybe word,
such as grammatical context for the next token or word. The remixing stage of
the GRCE channel is expected to quickly saturate the channel, so that, for the
most part, only information that is actively pushed forward by each position is
going to survive. In short: we expect the GRCE channel to implement various
forms of state machines.

For XCTX channel on the other hand we first squeeze the M vector into a n_xctx/2
dimensional vector space before the MLP. Resampling that by projecting back to
n_xctx followed by ReLU is exactly enough to fuly ReLU-decompose the n_xctx/2
wide channel. There is no down-projection after the ReLU layer, we stay in
n_xctx, just perform a single linear from n_xctx to n_xctx, and then use a
direction-preserving norm for the recurrent path, so no noise is introduced
into the channel that is not intentional signal interaction, because we can
always learn n_xctx (almost) linearly independent row/columns in W, whenever
independent channels in the XCTX recurrent path are desired. This path is meant
to be able to accumulate information over a span of positions and just carry them
forward in time for as long as bandwith is available in the path, with new
information cleanly overwriting or adding to older information, without adding
any "architectural noise" into the critical (recurrent) path in the process.


## Default train/eval batches and its row types -- (updated; implementation not up-to-date)

**`normal`**
  the baseline path: GRCE, XCTX, and attention all enabled with the standard causal mask.

**`decode`**
  disables both GRCE and XCTX entirely so the GPT core behaves like a pure Transformer.

**`encode`**
  disable GRCE and run XCTX in "encode mode" (see description of XCTX below);
  run the Transformer in encoder mode (no causal mask) so every token can
  attend bidirectionally before the final position predicts the first token
  beyond the block. (the XCTX output is unused in this row type, but it is used
  in `recode` rows):

**`recode`**
  a hybrid of `encode` and `decode`: the first BLOCK_SIZE//2 positions form an
  `encode` sub-row and the remaining positions are a `normal` sub-row.
  attention does not span accross the sob row-boundary. so non-masked attention
  in the `encode` sub-block can only query other positions in the `encode`
  sub-block, and causal masked attention in the `normal` sub-block can only see
  the positions left of it within the `normal` sub-block, not see all the way
  further left into the `encode` sub-block. the `encode` subblock is only
  linked to the second subblock via GRCE and XCTX. The GRCE input vector for
  the first `normal` position is simply created from sampling the last `encode`
  position and setting the recurrent input for that stage to zero. The XCTX
  output signal of the `encode` block is calculated by runnig the entire
  recurrent XCTX pipeline for the entire `encode` sub-block, but without the
  XCTX "bias injection".

- **`noxctx` / `puxctx`**
  remove the wide XCTX signal either for the entire row (`noxctx`) or by
  puncturing it at a single random timestep (`puxctx`) while GRCE remains
  active.

- **`noattn` / `puattn`**
  shut attention off entirely (`noattn`) or mask a single timestep’s ability to
  transmit forward (`puattn`) so the recurrent channels have to carry the load.

For training we prepare batches of BATCH_SIZE sequences. Of these we dedicate 1
sequence per batch to each of: `encode`, `recode`, `noxctx`, `puxctx`, `noattn`,
and `puattn`. Then we use `decode` for (BATCH_SIZE//2 - 6) rows in each batch,
and finally use `normal` for the remaining (BATCH_SIZE+1)//2 rows.  We call
this batch composition a *default batch* and it is used in training and
evaluation by default.

(Or simply put: the *default batch* optimizes for `normal` and `decode`, but
also adds one of each of the other row-types in each training block, to create
knock-out/drop-out type scenarios that drive learning towards robust networks
that utilize attention, grce, and xctx to stabalize each other and create
stable models that are easier to debug.)

The reported and logged loss values {train,test}_loss_target are the loss value
for an evaluation of such a "mixed" batch, our true objective function that we
train and optimize for.

The loss values {train,test}_loss_normal are based on the same batch, but only
using the loss values from `normal` rows.

The loss values {train,test}_loss_encode are based on the one loss values from
the two `encode` rows in each batch, and so forth.

All these losses a logged in the `loss_hist` array in the .pt file. Each record
contains the loss numbers as well as the step count, total training time so far,
a unix timestamp, and the cursors for train and eval corpus.

In addition to the 'train' subcommand there's also an 'eval' subcommand. For
example, `grce.py eval encode` will pull STEPS*BATCH_SIZE*BLOCK_SIZE tokens
from the test corpus (train coprus when `eval --train`), without advancing the
cursor for that corpus, and the run STEPS batches full of `encode` rows. Then
log the results and also store them in a `eval_hist` array in the model .pt
file, using a record with the following fields:
	step = number of traing steps so far (same as in `loss_hist`)
	train_wall_seconds = total trainig time so far (same as in `loss_hist`)
	unix_time = timestamp (same as in `loss_hist`)
	rowtype =  for example "normal"
	train_cursor = current cursor position in train corpus (if --train mode)
	test_cursor = current cursor position in test corpus (uness --train mode)
	seq_tokens_losses = array with STEPS*BATCH_SIZE arrays, each with 2*BLOCK_SIZE+1 entries:
		token_0, loss_0, token_1, loss_1, ... token_{n}, loss_{n}, token_{n+1}
	min_loss = min of the STEPS*BATCH_SIZE*BLOCK_SIZE loss values
	max_loss = max of the STEPS*BATCH_SIZE*BLOCK_SIZE loss values
	mean_loss = mean of the STEPS*BATCH_SIZE*BLOCK_SIZE loss values
	stddev_loss = standard deviation of the STEPS*BATCH_SIZE*BLOCK_SIZE loss values
	median_loss = median of the STEPS*BATCH_SIZE*BLOCK_SIZE loss values

The tokens in seq_tokens_losses are strings, the loss values are floats. For "encode"
there is only one loss value in the second to last position, for predicting the
first token of the next sequence, which is found in the last position of the array..

Further there is also a 'test' subcommand that evaluates the model on a single
block of the specified row-type (per default: `normal`), and prints verbose and
detailed token-level debug information about that evaluation. Use `test --size N`
to artificially reduce the block size to de-clutter the output of the command.


## Rotating position embeddings with paging -- (updated; implementation not up-to-date)

Instead of just BLOCK_SIZE position encodings we reserve BLOCK_SIZE*PAGE_COUNT
position encodings. (These position encodings form an "infinite loop": the
successor of the last position encoding is simply the first position encoding again.
(The default value for PAGE_COUNT is 8, but we currently only train for
sequences up to a length of PAGE_COUNT // 2; see below.)

In training we pick a new random start position within the 0 .. BLOCK_SIZE*PAGE_COUNT-1
range for each sequence, so the entire range incl. "wrap around" at the end of the
range is learned quickly, even tho only BLOCK_SIZE encodings are using in each
batch.

We define a new batch format to train for larger inputs: the *pages batch*.

A *pages batch* has `normal` rows of length `PAGES_BLOCK_SIZE := min(PAGE_COUNT // 2, BATCH_SIZE)*BLOCK_SIZE`,
again with random start positions. The effective `PAGES_BATCH_SIZE := BATCH_SIZE*BLOCK_SIZE // PAGES_BLOCK_SIZE`
for a *pages batch* is scaled down to keep a *pages batch* within the size of a *default batch*.


## Training and evaluation with pre-evaluation -- (this is future work)

We add a `--pre-eval` CLI option. For that mode we define a *pre-eval batch*,
that is evaluated before training on or evaluating a *default batch*.

The *pre-eval batch* contains a 50/50 mix of `encode` and `normal` blocks
and is evaluated on the current block of tokens for each training step or
evaluation during training, and then the final recurrent GRCE and XCTX vectors
generated by the last position of each block are extracted.

Then we create the actual training or eval batch, and we use the extracted GRCE and
XCTX vectors as recurrent inputs for the first position in the following block,
in 75% of the cases where that block is a `normal` block. (Note that we can
never run the first block in a batch with pre-eval input values, because we
have not evaluated the block before that during pre-eval.) We ensure that there's
always at least one case of normal-with-encode-pre-eval, one case of
normal-with-normal-pre-eval, and one case of normal-without-pre-eval in each
train or eval batch with --pre-eval enabled.

For all reported loss values, in evaluation steps, we calculate the `loss_hist`
{train,test}_loss_normal values using only the normal-without-pre-eval blocks,
and add the new {train,test}_loss_pre{norm,enc} values, that are calculated using
only the normal blocks with normal-pre-eval or encode-pre-eval respectively.


## Thinking Models -- (this is future work)

Standard transformers have a structural limitation: attention only connects
tokens across time *within the same layer*. Information computed in higher
layers at position t cannot directly influence lower layers at position t+1.
Any cross-layer temporal influence must be re-encoded into the token stream and
reprocessed bottom-up, which is indirect and lossy. The current state of the
art for mitigating this is Chain-of-Thought (CoT), which trains the model to
emit intermediate reasoning steps. However, CoT is not an architectural feature
of large language models; it is purely a learned behavioral pattern and does
not introduce explicit internal state or compute control.

GRCE and XCTX already remove this limitation without introducing any notion of
“thinking”. By sampling activations from all layers at a position, mixing them,
and injecting the result into any layer of the next position(s), they allow
information to cross layer boundaries across time explicitly. The entire
context discovered at one position becomes available to subsequent positions in
a layer-agnostic way.  This can free attention heads to focus on retrieval,
alignment, or comparison, rather than on carrying state forward, and it also
enables the *next position* to rebroadcast that information from a lower layer
if additional compute or restructuring is useful.

Thinking is therefore not the same as reasoning. Reasoning is the sequence of
transformations the model applies to information, as it summarizes it into more
new tokens. Thinking is the allocation of time and compute that determines how
many such transformations can be applied to a position before the model must
commit to a prediction.

There are two complementary ways to allocate thinking time. One is explicit and
fixed: duplicate tokens and positions and annotate them with `think:n/k`,
telling the model exactly how many think steps exist and which one it is
currently in. The other is adaptive: guarantee availability via `think-avail`
and let the model request more time by predicting the `<|think|>` token. In
both cases, the crucial point is that the model knows *in advance* whether at
least one more time slice is available, so it can safely postpone commitment.

Because of GRCE and XCTX, multiple passes over the same input position are not
redundant. Each additional stack runs with updated recurrent state, so later
think steps do not simply repeat earlier computations. GRCE provides
low-bandwidth control over phase and strategy, while XCTX carries
high-bandwidth accumulated context forward. This turns repeated stacks into a
genuine multi-step process rather than a redundant loop.

XCTX in particular enables cross-layer interaction across time. Signals sampled
from different layers are mixed and remixed before updating the recurrent
state, so an update to the XCTX vector can depend on the *joint presence* of
signals from multiple layers. As a result, thinking longer is not about doing
the same work twice, but about enabling conditional, staged computation whose
effects can propagate far forward in the sequence. One especially interesting
consequence is that later positions — far downstream — may see reduced loss
because they can rely on information that was explicitly stabilized and refined
during earlier thinking steps, rather than having to reconstruct it again
through attention alone.


## Non-token embeddings -- (updated; implementation not up-to-date)

(the following names for non-token embeddings are used for
documentation, comments, and log messages. the syntax looks
similar to the syntax we are going to use for our special
token, but use [] instead of <> to distinguish them from the
embedding names that correspond to special tokens below.

[|pos:0|] [|pos:1|] ... [|pos:BS*PAGES-1|]
  position embeddings for the max BS*PAGES positions in a sequence

[|think:1/2|] [|think:2/2|]
  additional "think" embeddings for think2x mode, in think2x
  mode we only use BS/2 position embeddings and input tokens,
  double each of the BS/2 input token+position encodings so
  we are back to BS elements in our block, and then add
  [|think:1/2|] to the even and [|think:2/2|] to the odd
  positions.

[|think:1/4|] [|think:2/4|] [|think:3/4|] [|think:4/4|]
  additional "think" embeddings for think4x mode

[|think-avail|]
  we add this learned embedding to all positions where we explicitly
  want to allow the model to request an additional think slot by
  predicting the <|think|> token (see below). (This is a guarantee.
  There's no guarantee that even more thinking time will be made
  available after the next position, but when we add this embedding
  to the input of a stack, the stack can decide early to do more
  thinking and can then confidently do whatever the model wants to
  do, when it knows, there will be at least one more time slice
  before it has to make up its mind.

<|@:> ... <:@|>

  it's a token and not a non-token embedding, because we might
  want to add it to training data in order to teach the model
  when to request additional thinking time. The model is trained
  to only do that, when [|think-avail|] is present on the input,

<|p7|> <|p6|> <|p5|> <|p4|> <|p3|> <|p2|> <|p1|> <|p0|>
  process-tokens. no special handling in the architecture. we simply
  train the model that whenever it sees <|pN|>, the next tokens will
  always be <|p{N-1}|> ... <|p0|>. this means injecting such a process-sequence
  will effectively free the model from spending any compute on predicting the
  immediate next token for the next N positions, and is instead free to use its
  attention heads and compute to re-structure what it knows and make that
  re-structured information available to the later positions in the sequence,
  in whatever way of form turns out to be usful within the training corpus.
  In a transformer without recurrent path this exercise would be pointless.
  But with the added recurrent GRCE and XCTX channels, just adding those
  process-tokens is already enough to enable a simple first mode of "additional
  thinking time". (We usually add such a sequence in training in a special
  training mode, where we add them at random positions in the corpus, always
  between a puncuation mark (!?:;,. or ") and a whitespace that follows it.


## Special GRCE embeddings -- (this is future work)

We define the following learned GRCE embeddings and corresponding simple on-off state machines:

{tokipona}
  set by <|tokipona:> and </tokipona:>, cleared by <|english:>, </english:>, <|//|>, and <|----|>

{english}
  set by <|english:> and </english:>, cleared by <|tokipona:>, </tokipona:>, <|//|>, and <|----|>

{lq}
  set by <|lq:>, cleared by <:lq|> and <|----|>. Likewise:

{hq}, {!}, {?}, {*}, {-}, {=}, {/}, {@}
  set by <|...:>, cleared by <:...|> and <|----|>.

During training when --learn-grce-embeddings is present, we parse the
BLOCK_SIZE (or PAGES_BLOCK_SIZE) sequence for each block and maintain a state
variable for each of these GRCE embeddings. Initially they are all zero.
Whenever we see a "set" token, we set the corresponding variable to +1,
whenever we see a "clear" token, we set the corresponding variable to -1. For
each step we look at the non-zero states and then either add the objective
G.dot(embedding) > 1 for all GRCE state embeddings that are expected "ON" (+1), and
G.dot(embedding) < 1 for all GRCE state embeddings that are expected "OFF" (-1).

## Fix self-attention prefix computation

The current `grce.py` implementation is *logically* left-to-right but
*computationally* prefix-recomputing. In `forward_autoreg`, the model loops
over time `t`, but at each step it calls the Transformer core on the **entire
prefix** `0..t`. Inside the core, causal self-attention is implemented with
explicit `(T×T)` score matrices and masks, so every layer is evaluated
**layer-by-layer over all prefix positions**. This enforces O(T²) work and
prevents true streaming execution, even though only the activations at the
current position are actually used.

The GRCE/XCTX channels themselves are already compatible with strict
left-to-right semantics. Context → Transformer injection is done via
**per-layer additive bias vectors applied only at the current token position**,
and Transformer → Context updates consume **per-layer activations at the
current position only**. No GRCE/XCTX computation depends on future tokens or
on earlier positions being recomputed, so their logic does not require
prefix-wide evaluation.

To obtain true left-to-right evaluation, the Transformer core must be
refactored to an **incremental, KV-cached forward**. Each time step should run
the *full layer stack for a single token*, appending that token’s K/V to
per-layer caches and attending only against cached past keys/values. The
GRCE/XCTX bias injection and state update can remain unchanged, now operating
naturally at each step after the token’s full stack has been evaluated.
